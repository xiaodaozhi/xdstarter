# 菜单宽度、吸附与紧凑交互研究

- 日期：2026-10-23
- 状态：研究记录；本轮采用方案见 [ADR-0015](../adr/0015-responsive-tile-columns.md)
- 关联：[Issue #48](https://github.com/xiaodaozhi/xdstarter/issues/48)
- 源码核查基线：`a9abf252a6668c431928b2bbad5cafd1801bef55`

本研究保存本轮动态宽度、Windows 10参考行为及文案范围的调查依据，不替代Issue中的进展和验收记录。调查时先比较了下列候选；后续用户已明确要求可用磁贴列数随窗口变化，因此采用显式schema4与56 DIP宽度吸附，决定和实现边界见ADR-0015。下文候选比较保留研究语境，不表示所有方案均已实施，也不作为运行验收通过记录。

## 当前宽度的实际约束

本节及后文“当前”均指上述调查基线；后续实现已按ADR-0015更新，不能将基线约束当作新版本行为。

[共享网格](../../design/tokens/tile-grid.json)定义小格48 DIP、间隙8 DIP、默认10列；步距为56 DIP，10列外框为552 DIP。三档磁贴外框分别为48×48、104×104、216×104 DIP。调整窗口或呈现容器不应拉伸磁贴或改变间隙。

当前宽度需要分成两层理解：

| 层次 | 当前实现 | 影响 |
| --- | --- | --- |
| 磁贴视口 | [Main.qml](../../../qml/Main.qml) 中 `groupsScroll` 已使用 `Layout.fillWidth: true` | 视口本身随窗口变化，并未被552 DIP钳制 |
| 分组呈现容器 | `groupsColumn` 的隐式宽度由 `TileGroup.width = group.width` 推导 | 分组标题与管理按钮的右缘仍停在552 DIP处 |
| 逻辑拖放网格 | [TileGroup.qml](../../../qml/TileGroup.qml) 的 `grid.width = group.width`；[TileGrid](../../../src/core/tile_grid.cpp) 返回10列宽度 | 磁贴位置与可用落点限定在10列内 |
| 窄窗口断点 | Main.qml 的 `compactLayout` 直接使用552 | 分区切换重复了C++已经掌握的网格几何知识 |
| 布局与保存 | [PrototypeService](../../../src/services/prototype_service.cpp) 的占位表、挤开与固定算法采用10列；[LayoutStore](../../../src/services/layout_store.cpp) 严格校验列坐标 | 增加可用逻辑列不能仅靠修改QML宽度完成 |

因此，直接拉宽ScrollView不会增加第11列落点；直接将磁贴容器拉伸也不能算新增了布局空间。当前完整约束见[磁贴布局](../tile-layout.md)与[数据持久化](../data-persistence.md)。

## 保留当前格式的动态视口候选

最小候选保留10列逻辑网格，将呈现宽度与逻辑宽度分开：

1. C++向QML提供共享逻辑宽度，或从现有共享网格属性计算，删除重复的552常量。
2. 分组外层和 `groupsColumn` 使用 `max(实际可用视口宽度, 逻辑网格宽度)`。组标题、分组管理按钮随外层右缘变化；磁贴仍保持原始坐标与尺寸。
3. 窄窗口保留横向滚动，焦点与拖放坐标仍基于原逻辑网格。改变窗口尺寸不重写布局、不改变分组与磁贴ID、不触发布局保存。
4. 滚动条预留必须计入实际视口，避免外层宽度绑定产生“出现滚动条后又触发另一条滚动条”的反馈循环。

此候选改善区域与标题的动态宽度，但不会扩大单组的可用逻辑列数。设计验收时需要明确这个区别；如果用户要求宽窗口可放置更多列，应另行选择布局策略，不能将这个最小候选当作完整满足。

## Windows 10 的官方依据与未知部分

微软的[开始菜单自定义说明](https://support.microsoft.com/en-gb/windows/experience/personalization/customize-the-windows-start-menu?nochrome=true)在Windows 10章节说明，可拖动顶部或侧边边框调整菜单高宽。[2017年的Windows官方博客](https://blogs.windows.com/windowsexperience/2017/09/11/windows-10-tip-make-start-full-screen/)也说明可通过顶部与侧边调整大小。

[Windows开始布局文档](https://learn.microsoft.com/en-us/windows/configuration/start/layout)定义组列数量与组内格坐标，示例使用 `GroupCellWidth="6"`；[官方XSD](https://learn.microsoft.com/fi-fi/windows/configuration/start/xsd)的 `StartTileGroupCellWidth` 枚举包含6和8。这些是布局结构依据，不是交互缩放算法说明。

本次未找到微软公开定义交互吸附阈值、滞回、半档取整方向或各系统版本差异的资料。不能据此宣称某个56 DIP算法精确复刻Windows 10，也不能把XML中的6或8直接当作本项目的吸附档位。下面两种策略均是结合XDStarter共享几何提出的候选，不是已证实的Windows内部实现。

| 候选策略 | 几何与交互 | 格式影响及边界 |
| --- | --- | --- |
| 按56 DIP步距吸附窗口宽度 | 从固定快捷栏、目录、正文边距及滚动条预留构成的基准出发，将可变部分量化到共享网格步距；保持单列分组呈现 | 可保留schema3与10列；量化的是窗口和呈现宽度，不代表新增逻辑列。需要在设计中明确是XDStarter自定义规则 |
| 按完整分组列吸附 | 一组10列宽552 DIP，横向组间距若复用当前24 DIP，则每新增一个组列的增量为576 DIP；需设计分组跨列排布与顺序 | 可保持组内坐标和schema3，但会改变分组的呈现组织、跨组导航和拖放映射；当前需求尚未明确要求分组横向换列 |

前一种候选的具体基准必须来自运行时实际分区，不应简单对整个外窗宽度除以56。后一种的576 DIP也只是采用现有组宽和组间距得出的项目值，不是Windows 10常量。两者不应在未说明的情况下混用。

## 原生缩放与屏幕边界

当前[桌面几何函数](../../../src/platform/desktop_platform.cpp)与Windows自有菜单HWND的缩放处理已经共同保持非拖动边固定。宽度吸附与最大尺寸应继续经过这一条几何链路，而不是在QML和Win32分别计算。

候选规则以扣除任务栏后的工作区为上限，再为可见面板四方预留共享 `screenGapDip`，当前为8 DIP。透明阴影留白24 DIP不计入可见面板的屏幕边距。最大宽高必须由这个有效区域决定，不能仅在重开时重新定位，也不能为凑齐吸附档位越过上限。

拖动左边时保持右边，拖动右边时保持左边；顶部、底部与角部遵循同样规则。先在有效候选档位中选择宽度，再在实际工作区内夹限；若工作区无法容纳最小尺寸，应明确可达性降级，避免最小尺寸与屏幕上限互相拉扯。四边任务栏、居中对齐、负坐标显示器及DPI换算均复用现有平台边界。

## schema兼容边界

当前schema3严格校验字段及10列坐标，偏好只允许既有主题字段。前述动态呈现和分组分栏均可不改变持久化格式：缩放窗口不等于布局编辑，呈现宽度也不应被伪装成磁贴数据写入。

将 `column > 9` 的真实位置、每组列数或窗口宽度偏好写入布局时，必须先更新格式与兼容设计。直接在schema3中放宽坐标或增加字段，会使旧程序把输入当成损坏配置，不能借用“旧程序忽略未知字段”的假设。应保留schema1/2/3读取、旧文件原始备份与未来版本只读保护，沿用[ADR-0011](../adr/0011-tile-display-names.md)既有原则。本轮已选择schema4，决定见ADR-0015；本节保留格式升级的判定依据。

## 快捷按钮间距候选

[ShortcutRail.qml](../../../qml/ShortcutRail.qml)底部四个快捷按钮目前各为48×48 DIP，按钮间隔8 DIP，普通图标24 DIP。候选将四按钮间隔降至0，使整体高度从216降为192 DIP；仍保留48×48命中区、图标尺寸、顶部独立头像与两端边距。这样收紧视觉间距而不缩小交互目标，最终数值随设计验收确定。

## 产品文案的分隔范围

本轮要求产品自有文案不再使用中点作为分隔符。源码核查时共有9处运行时内置文案：Main.qml中的应用提示、搜索描述及三档尺寸文字，TileButton.qml的提示，LayoutImportDialog.qml的摘要，以及menu_controller.cpp的目录更新附加状态。

候选使用换行、中文逗号或尺寸括号。尺寸文字按用户给定名称采用“小磁贴 (1×1)”、“中磁贴 (2×2)”、“宽磁贴 (4×2)”。导入摘要可用逗号和换行区分数量与格式信息；提示中的名称与类型可分行显示。

这项限制针对产品生成的分隔文案，不应清洗或改写用户定义的磁贴名称、分组名，以及系统提供的应用名称。当前交互与品牌设计生成器也含有旧分隔写法，新候选设计不应沿用；历史探索资产不作为新候选的验收依据。

## 候选方案的验证要求

验证应优先扩展现有单元测试与GUI夹具；测试自有HWND的原生消息可补足Win32适配边界，不使用全局合成输入。以下为方案成立所需的检查范围，不代表这些新增行为已实现或通过：

- 动态呈现：宽窗口下分组标题与管理按钮跟随视口；窄窗口内容可达；滚动条无反馈循环；搜索返回和焦点滚动恢复正常。只改变窗口宽度时，布局快照、稳定ID和共享磁贴几何保持不变。
- 吸附与限界：左右及四角缩放、四边任务栏和两种对齐、五档DPI、负坐标；档位阈值两侧、最小与最大尺寸、工作区不足、四方边距、阴影留白、非法矩形和整数溢出；非拖动边不跳位。
- 原生适配：扩展已有自有HWND sizing消息夹具，核对 `WM_SIZING` 与后续窗口定位实际使用同一吸附和屏幕上限结果。
- 若选择分组横向分栏：额外检查组顺序与稳定ID、跨栏拖放坐标、键盘跨组导航及滚动状态。不能仅凭分栏截图判定编辑语义成立。
- 快捷栏与文案：相邻命中区不重叠、图标与可访问名称保留；产品内置文字使用新的分隔方式，同时完整保留用户及系统提供的名称。
