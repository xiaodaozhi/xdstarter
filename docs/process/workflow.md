# 产研流程

## 单一跟踪入口

需求、Bug、研究与交付任务统一使用 GitHub Issues。Issue 保存场景、验收、负责人、优先级、进度与阻塞；PR 保存实现、审查与验证；文档保存稳定规格与决策。

聊天中形成的新需求或 Bug 也应先查重并建立/关联 Issue，再更新文档和实现。没有实际缺陷证据时使用研究任务，不虚构 Bug。

## 从提出到交付

1. **提出**：使用模板，补齐问题/价值、范围、验收或复现。进入 `status:needs-triage`。
2. **分流**：确定 type、priority、area 和 Milestone；缺信息在原 Issue 追问。达到可开发条件后标 `status:ready`。
3. **实施**：认领负责人，切分支，设 `status:in-progress`。范围变化或阻塞及时写入原 Issue，并链接相关任务。
4. **评审**：PR 链接 Issue、相关设计与测试证据。架构变更含 ADR；功能变化同步产品与技术文档。
5. **验收**：按 Issue 标准检查实际行为；需要真机的内容提供 Windows 构建与环境记录。
6. **关闭**：全部标准满足后由 PR `Closes` 或维护者关闭；仅交付部分使用 `Refs` 并保留 Issue。

阻塞时使用 `status:blocked`，注明阻塞任务、需要的输入和恢复条件。解决后回到 ready/in-progress。已关闭 Issue 无需保留进行中的 status 标签。

## 可开发条件

清楚说明目标用户与场景、范围、不做什么、验收、受影响文档与关键依赖。研究任务需要明确要回答的问题和结果形式，不要求先知道答案。

## 分层验证与 CI

提交和推送前运行 `python3 scripts/check_repository.py`，并按改动完成本地验证；影响结果的源码或配置变化后重新验证。无需安装 Git 钩子。文档和设计检查链接、JSON 与受影响的生成资产；核心逻辑、状态转换和持久化运行相关构建及测试；C++/QML 修改构建相关目标并检查交互与布局；Windows 系统接管、安装与发行按实际影响选择隔离环境和针对性验证。工具或环境缺失时记录未执行项目，不以其他平台或静态检查冒充通过。

[Repository checks](../../.github/workflows/repository-checks.yml) 随 PR、main 推送及手动触发，执行仓库和工具检查；它不构建产品。同一 PR 的旧日常运行可以取消。完整 [Application build](../../.github/workflows/application-build.yml) 仅手动触发，保留 Linux 核心、Windows 构建、实验、打包和证据汇总，适用于相关变更、排查及发行准备；以被验证的提交、运行和实际结果为准。手动工作流不自动取消，不能把未触发、失败或取消记为通过。按需执行方式和验证边界见[测试策略](../technical/testing.md)。

根据变更尽量检查实际应用或截图；真实 Explorer、输入法、物理显示器、系统对话框与安装等按风险和可用环境验证并记录限制。Server 夹具、离屏或模拟输入不等于 Windows 11 真机和物理输入通过，也不自动批准发行。无需为每次普通变更套用固定人工矩阵；Issue 中实际未解决的产品问题和必要验收继续跟踪。

## 研发周期收尾与复用

本机使用 `toolchain.json` 的共享 `build/tooling/` 和 `build/Qt/`；`qmllint` 使用同一 Qt SDK 的 `bin`。先检查已有环境并复用，仅在验证其他版本或隔离需求明确时使用显式 Qt 参数；不要为每个任务重复下载一套。宿主编译器、Windows SDK 不由上述缓存替代，具体入口见[开发环境](../technical/development.md)。

新周期用 `python3 scripts/cleanup_cycles.py --init issue-154` 创建 `build/cycles/issue-154/`，在 Issue 或工作记录注明用途。验证和合并后，保留待复验数据、候选、共享工具和其他任务的文件；确认周期产物可丢弃后运行 `--path issue-154` 预览，再运行 `--path issue-154 --apply --yes` 删除。使用过的分支和 worktree 先核对归属、未提交工作与合并状态，只有不再需要且安全时才清理；已有其他工作不因周期收尾被删除。

兜底命令 `python3 scripts/cleanup_cycles.py --stale-days 30` 只预览已登记的过期周期，不自动删除；逐项核实后使用显式 `--path` 删除。历史未登记输出不能由年龄或名称自动判定为安全；查清归属后，可用 `--legacy-path 单个顶层名称` 预览，再显式追加 `--apply --yes`。工具拒绝共享 Qt、工具、标准构建、候选、验证、worktree 等保护目录、已登记 worktree 的父子路径，以及含链接、重解析点或 Git 元数据的目录。无法核查时保留并记录。GitHub runner 的手动任务不能清理开发机，本入口在本机执行。清理后检查 `git status --short`。不要整棵删除 `build/`，也不要移动或清理仍有用的证据。

构建和 QML lint 的诊断按实际日志逐项判断：可修的工程配置、类型或代码问题应修复并运行对应测试；环境插件限制等保留原因与范围，不通过全局屏蔽警告或改变界面语义使日志变绿。CI 工作流入口变化要同步验证触发契约与实际运行，失败时核对当前 head，不把旧版检查当作通过。

## 审查与合并

使用短生命周期分支，默认 **merge commit**，保留分支中的原始 commit 及 SHA。Conventional Commits 表达各项变更。合并前完成当前 PR head 的适用检查、本次 PR 声明范围的验收和必要审查；只有 Issue 的全部标准满足后才关闭，部分交付使用 `Refs`。代码变更尽量由另一维护者审查，单维护者项目可记录自审与实际验证证据。用户明确指定其他合并方式时，以该次指令为准。

## 开发任务的默认交付

已授权的开发、修复、“按项目约定推进”及“提交推送”任务，由代理持续完成以下步骤，无需用户分别提醒创建 PR 或合并；本约定跟踪于 [Issue #20](https://github.com/xiaodaozhi/xdstarter/issues/20)：

1. 按 Issue 范围实现并完成适用的本地检查、必要的 Windows 真机验收，整理可审查的证据。
2. 提交、推送任务分支并创建关联 Issue 的 PR，记录实际完成范围、验证结果和未覆盖事项。
3. 跟踪 PR 当前 head 的适用 CI 和必要审查。失败时先处理并重跑；head 改变后重新检查，不以旧提交的结果代替新版本通过。检查缺失或外部条件阻塞时如实说明，不将待运行视为通过。
4. 检查、审查与验收满足后，锁定已验证的 head，以 merge commit 合并到 `main`；遵守现有仓库规则与合并门槛。
5. 核对原始提交保留在 `main` 历史中，记录 PR、合并提交与验证证据；完整交付关闭 Issue 并移除进行中的状态标签，部分交付保持 Issue 打开。
6. 工作区状态允许时，将本地 `main` 快进同步到远程并报告结果；有无关改动或无法快进时保留现场，说明实际状态。

用户明确指定只实现、仅提交推送、草稿 PR 或暂不合并时，停在对应边界；纯讨论、只读审查和尚未授权实施的方案不触发提交与合并。需要用户处理的真实阻塞应说明原因，已获得的交付授权不重复确认。

此流程由代理在开发任务执行期间跟踪检查并调用 GitHub 合并接口；代理停止执行后，没有常驻合并任务。当前仓库的 GitHub Auto-merge 未启用，本流程的 PR CI 只负责检查，未配置自动合并 job；该执行流程不依赖开启 Auto-merge，也不修改工作流权限或分支保护设置。仓库配置变化时应同步更新此处的执行说明。

Branch protection 和组织级 Projects 不在本次初始化中强制修改。仓库级 Issues、Labels、Milestones 和模板即可支撑当前规模；需要额外权限或工作流时另开任务。

完成定义见[DoD](definition-of-done.md)，分类规则见[Issue 管理](issue-management.md)。
